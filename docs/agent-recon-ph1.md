## 1. Assignment

- File `lib/orders/assign.ts`. Exports: `DESIGNER_SLA_HOURS = 24`, `createAssignment`, `rankCandidates` (pure), `runAutoAssign`, `findNextEligibleDesigner`, types `Candidate`, `RankedCandidate`. `loadRankedCandidates` is NOT exported.
- **`runAutoAssign(tx: Tx, order: {orderId: string; businessId: string; assignedBy: string | null}): Promise<{assigned: string | null}>`**
  - Reads style from the first `order_items` row (`orderItems.style`), builds ranked candidates, assigns the top one via `createAssignment`. Returns designer user id, or `{assigned: null}` when nobody is eligible (order stays `ready_to_assign`, no active assignment, shows in VA "Unassigned"/"Needs VA Review").
  - `assignedBy: null` = system/agent. Must be called inside a transaction (`withSystemContext(async tx => ...)` from `lib/db`).
- **`createAssignment(tx, {orderId, businessId, designerId, assignedBy, dueAtHours?, reason?}): Promise<{assignmentId, dueAt}>`**: the one place an assignment row is created. Sets prior active row `active=false`, inserts new `assignments` row (`dueAt = now + 24h` default), then calls `sendDesignerBrief` (`lib/notifications/designer-events.ts`), which queues an `alpha_events` row `designer.brief`.
- The ranker DOES pick the best designer automatically. Hard filters: `ordersAssignedToday < dailyCapacity`; `maxActiveOrders === 0 || wipCount < maxActiveOrders` (WIP = active assignments on orders in `in_design`/`awaiting_qc`); STRICT style match (order with a style goes only to designers listing it, order with no style is open to all). Sort: `rank` asc (designer_profiles.rank, lower wins) -> most remaining capacity -> lowest WIP -> best 30-day on-time rate (earnings vs orders.dueAt). Roster = `designer_businesses` join active `users` role `designer` join `designer_profiles`.
- **Quiet hours are NOT used in assignment.** `lib/designers/quiet-hours.ts` (`quietWindowEnd`, timezone helpers) only delays Alpha messages to the designer. Style catalog helpers in `lib/designers/styles.ts`; roster UI data in `lib/designers/roster.ts` (`getDesignerRoster`, `getRailDesigners`).
- DB writes by `runAutoAssign`: `UPDATE assignments SET active=false` (prior active), `INSERT assignments`, plus `INSERT alpha_events` via brief. It does NOT write `activity_log` and does NOT change order status (the transition or importer does that).
- Callers of `runAutoAssign`: `lib/orders/transitions.ts:269` (inside `runTransition` when `to === "ready_to_assign"`, `assignedBy` null if actor role `system`), `lib/integrations/shopify/orders.ts:522` (import), `app/(app)/orders/new/actions.ts:278` (manual order), `lib/orders/resolution.ts:423` (re-resolve), scripts/mock-pipeline.ts.
- Human "pick a designer" path: server action **`bulkReassignOrders(orderIds: string[], designerId: string)`** in `app/(app)/orders/actions.ts:242`. It does NOT call `createAssignment` (duplicates the logic inline: deactivates old, inserts with fixed 24h dueAt, writes `activity_log` action `order.assigned` or `order.reassigned` with `metadata {designerId, via: "bulk_orders_dashboard"}`, NO designer brief). Uses `requireStaff()`, `REASSIGNABLE_STATUSES` (awaiting_details, awaiting_photos, ready_to_assign, in_design, ...; see line 71), checks designer is in `designer_businesses` for the order's business. Catches unique violation `assignments_active_order_uq`. No API route for assignment.
- SLA sweep reassign: `lib/notifications/designer-sweep.ts` uses `findNextEligibleDesigner(tx, {businessId, style, excludeDesignerId})` + `createAssignment` (behind `ALPHA_ACTIONS_ENABLED === "true"`).
- Recommendation for the agent: call `runAutoAssign` (or `runTransition(... to: "ready_to_assign")` which calls it) in `withSystemContext`, then insert an `activity_log` row yourself with `actorId: null`.

## 2. Order intake

- Table `orders` (`lib/db/schema.ts:531`), default `status = awaiting_photos`. `source` enum etsy|shopify|manual. Unique `(shop_id, platform_order_id)`. Fields: `needsReview`, `uploadToken`, `dueAt`, `rawImport` (jsonb, full Etsy receipt), `archivedAt`.
- `orderStatus` enum: awaiting_photos, ready_to_assign, in_design, awaiting_qc, awaiting_approval, approved, printing, shipped, delivered, complete, on_hold, cancelled, triage, fulfillment_only, awaiting_details.
- **Shopify** (`lib/integrations/shopify/orders.ts`, function around line 360-560): status at creation = `cancelled`/`complete` if Shopify fulfilled/cancelled; `triage` (draft orders); `fulfillment_only` (non-portrait); else `ready_to_assign` if any line item has photo URLs (`anyPhotos`), else `awaiting_photos`. If `ready_to_assign && !needsReview && !suppressCustomerEmail && !archived && !done`, it auto-assigns right in the import tx (so Shopify orders are ALREADY auto-assigned at import). `needsReview = !email || fulfilmentConflict || (portrait && any item figure source "unresolved")`. Logs `activity_log` action `order.imported` with `photoCount`, `figures`, `assignedTo`, `autoAssigned`.
- **Etsy** (`lib/integrations/etsy/receipts.ts`, `etsyReceiptToInitialStatus` ~line 403): lands as **`awaiting_details`** (only header, no order_items, no photos) unless Etsy says shipped/completed/cancelled (-> complete/cancelled). Gmail-inbound Etsy sale notices also create `awaiting_details` (`lib/integrations/gmail/inbound.ts:651`). A VA completes it via `completeOrderDetails` (`app/(app)/orders/new/actions.ts:309`): fills figureCount/style/product/notes/photos, then `runTransition` awaiting_details -> ready_to_assign (if photos) or awaiting_photos; that transition triggers `runAutoAssign`.
- **"New, not yet assigned" statuses**: `awaiting_details` (Etsy, needs human details), `awaiting_photos` (waiting on customer photos), `ready_to_assign` (photos + figures present; assigned automatically if a designer is eligible, else sits with no active `assignments` row). Truest "unassigned" check: status `ready_to_assign` with no `assignments` row where `active = true`. Also `triage` / `fulfillment_only` are non-portrait, never assigned.
- **Photos**: table `assets` (schema line 665), rows with `type = 'reference'` (also `submission`, `final`), `storage = 'cdn'` (Shopify checkout URLs in `url`) or `'r2'` (`r2Key`, customer uploads / VA uploads), `orderItemId` nullable, `deletedAt` (retention). Count = `count(*) from assets where order_id=? and type='reference' and deleted_at is null` (same predicate used in `lib/uploads/data.ts:82,285`). Customer upload page: `lib/uploads/data.ts`, moves `awaiting_photos -> ready_to_assign` through the state machine after upload.
- **Ordered figure count**: `order_items.figure_count` (int, nullable = unresolved) + `figure_count_source` enum shop_rule|heuristic|manual|unresolved. Resolved at import by `lib/integrations/figures.ts` (`resolveFigureCount`, per-shop `shops.integration_config.figureRules[]`, optional heuristic; Etsy wrapper `lib/integrations/etsy/figures.ts`). Raw inputs kept in `order_items.options` (jsonb `ProductOption[] {name,value}`), `variation`, `raw_variations`. Sum across items = figures ordered. Trust only source != unresolved. Also `lib/orders/options-summary.ts`, `lib/orders/resolution.ts` (re-resolve).
- **Existing completeness/mismatch logic**: NONE for photo count vs figure count. Only presence checks: `lib/integrations/etsy/receipt-review.ts` `MissingField = "Customer email" | "Style" | "Reference photos"` (photoCount > 0 only); the `assertFiguresResolved` gate on `complete`, `assertHasSubmission` on awaiting_qc (`lib/orders/transitions.ts`); `lib/uploads/data.ts:121-123` builds the customer ask text "Upload N clear photos" from figureCount. Photo count vs figures is a new build. Note for pets/people a photo may hold several subjects, so a mismatch heuristic should flag not block.

## 7. Outbound email drafts

- `lib/email/outbox.ts` is READ-only (`getOutbox`, `getOutboxCount`, `getUnmatchedReplies`, `getMailHistory`, ...). Creation is in **`lib/email/dispatch.ts`**. Private `insertRendered(tx, {businessId, orderId, customerId, key, status: 'draft'|'queued', proofId?, orderNumber, ctx, vars})` renders the template and inserts a `messages` row (`direction outbound`, `channel email`, `templateKey`, `address`, `subject`, `body`).
  - DRAFT (waits for VA one-tap approve in outbox): `prepareProofForApproval`, `draftRevisionReceived`, and **`queueStageEmail(tx, order, key, vars)`** which is `draft` unless `businesses.stage_email_auto_send` then `queued`. Keys: order_received, in_design, printing, shipped, proof_reminder.
  - QUEUED (auto-flushed, no approval): `queuePhotoRequest(tx, order)` (key `photo_request`, vars `upload_link`), `queuePhotoReminder(tx, order)` (key `photo_reminder`). Both return message id or null (no customer email).
  - Sending: `sendMessage(messageId, {approvedById?, markRetryableFailed?})` sends via business Gmail; `flushQueued(businessId?)` sends queued rows. All sends gated by `businesses.email_sending_enabled`, plus `lib/email/suppression.ts`, `backlog-guard.ts`.
- **Photo chase template EXISTS**: `photo_request` and `photo_reminder` in `DEFAULT_TEMPLATES` (`lib/email/templates.ts`, lines ~16 and ~157) with `{{first_name}} {{order_number}} {{business_name}} {{upload_link}}`; `emailTemplateKey` pgEnum in schema line 112; DB overrides in `email_templates`; helper `uploadUrl(uploadToken)`. There is NO "wrong number of photos / need N more" template. For the mismatch case either add a new `emailTemplateKey` enum value (migration needed: `ALTER TYPE ... ADD VALUE`) plus a `DEFAULT_TEMPLATES` entry and a `queueX` function with status `draft`, or reuse `photo_request` via a draft-status variant (`insertRendered` is not exported). Also `lib/email/template-meta.ts`.
- Reminders sweep: `lib/reminders` (48h photo reminder), route `app/api/cron/reminders`.
